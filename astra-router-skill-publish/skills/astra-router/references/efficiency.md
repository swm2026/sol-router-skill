# Evidence-based efficiency review

Read only for a requested cost audit or demonstrated recurring overhead. Optimize total completed-task cost and rework, not the smallest possible output.

## Evidence to collect

Use available completed-run evidence first. Record task class, parent model if known, route, brain invocations, executor starts/resumes, repeated reads/checks, elapsed time and acceptance result. Record input, cached-input, output and reasoning usage only when the runtime supplies them; preserve its definitions and avoid double-counting totals. Missing fields are unknown, not zero. Account quota percentages cannot attribute tokens to one task.

Keep the default trace one line; do not add a verbose log or persistent file to every task. For a requested audit, summarize comparable runs in a small table.

## Find waste in this order

1. Brain invoked despite a clear plan: try direct Terra/Luna.
2. Astra doing parent orchestration on ordinary engineering: suggest a Terra parent on the next user-started task.
3. Sol and Astra both approving routine work: keep only the role resolving a concrete uncertainty.
4. Repeated raw evidence: one source-backed packet plus deltas.
5. Recreated executor: resume the same one with existing evidence.
6. Long unrelated history or repeated instruction reads: focused task boundary and on-demand references.
7. Excessive reasoning/output: lower effort only for bounded decisions; retain higher effort where failures cost more.

## Validate an optimization

Do not benchmark automatically on live projects. When a comparison is authorized, use representative mechanical, ordinary debugging, planning, architecture and risk cases on isolated disposable fixtures. Keep starting state, acceptance and runtime settings comparable; vary one routing choice at a time. Include failures, repeats and all parent/child usage. No deployment, real accounts or broker writes.

Distinguish static rule checks, dry routing judgments, actual agent execution and measured usage. A routing exercise proves no token savings. Compare quality and completion first, then observed total cost/latency; do not extrapolate one tiny task to all work.

After a completed task with visible waste, offer at most one evidence-backed improvement. Do not silently edit installed skills or memories, change authorization boundaries, or create recurring monitoring. Never fabricate savings when usage data is unavailable.
